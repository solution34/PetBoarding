## 1. 项目描述与目标

本项目拟开发一个宠物寄宿 Web 系统。宠物主人在线维护宠物资料、提交订单、查看订单进度及照护记录；前台接待员提前核实房间可接待情况、维护并开放可预约房源；主人查询房源后自主预约并支付全款，线上不逐笔等待前台审核；主人带宠物到店后，前台核对并正式接单，再直接分配照护员、办理入住、结算及离店结单；宠物照护员查看分配给自己的订单、安排和执行照护、登记结果及上报异常；店长主要处理突发事项并查看每个订单的进度，在异常处置需要时调整照护安排；系统管理员负责账号及角色权限管理。

系统以寄宿订单为主线，记录预约、接单、入住、照护、异常处理、结算及离店过程，使主人能够远程了解寄宿情况，店长能够统筹门店业务，每只寄宿宠物有明确的负责宠物照护员，照护和异常处理过程可查询、可追踪。

本轮进一步确认：一张寄宿订单对应一只宠物和一个实际房间，先线上预约、后线下正式接单。前台先维护可预约房源，主人浏览房源、选定日期后由系统计算该期间的可用房间，再填写预约要求；提交时系统复核可用性并预留一间实际房间，主人在线支付全款后预约成功，但不记为正式接单；主人带宠物到店，前台核对并确认实际接收后才算正式接单，随后直接分配本次寄宿的主负责照护员，日常派单无须店长审批。正式接单与入住可以连续办理，分别保存接收及实际入住记录；实际入住后才开始照护。预约与正式接单关联同一订单，不要求主人再次填写一份订单。一名照护员可照护多只宠物；前台办理日常转派，店长可在突发事项处理中调整人员，转派均保留交接记录。

支付方式已确认改为线上预约时通过真实微信或支付宝支付预约寄宿费用全款。所选日期及房间通过系统校验，且平台确认全款支付成功后，预约成功、等待到店；到店核对付款结果，不再次收取同一预约费用。原定金、离店补尾款及24小时未付定金取消规则取消。计费标准、具体支付平台、未完成付款时的预留时限，以及取消或服务变更后的退款和费用调整政策仍待明确。

需求来源为用户在本轮会话中的业务说明与确认，并非真实门店访谈。课程要求见[课程与提交说明](../03_实验报告/课程与提交说明.md)。

## 2. 范围与角色

| 角色 | 主要职责 | 权限边界 |
|---|---|---|
| 宠物主人 | 维护宠物资料、浏览房源并按日期查询空房、提交和查看预约、带宠物到店办理正式接单、预约时支付全款、查看照护记录并接回宠物 | 仅访问本人及本人宠物的相关信息 |
| 前台接待员 | 提前核实房间可接待情况，维护房间资料和开放状态；到店核对后正式接单，直接分配照护员，登记入住与物品，核对结算并办理离店结单 | 可直接办理接单和派单，无须店长审批；发现无法安排人员等突发问题时上报店长 |
| 宠物照护员 | 查看负责的订单，安排和执行照护事项，登记宠物情况、上报异常并办理照护责任交接 | 按分配职责办理照护业务；跨员工代办权限待明确 |
| 店长 | 查看每个订单的进度及照护情况，处理突发事项、联系主人并记录结果；异常处置需要时调整照护安排 | 可查看门店全部订单及对应入住、照护、付款和离店进度；有异常处理及紧急调配权限，日常派单无需其审批 |
| 系统管理员 | 管理账号及角色权限 | 不因管理员身份自动取得门店业务操作权限 |

宠物是业务对象，不是使用系统的参与者。远程查看指订单及已登记的照护信息。视频监控、在线诊疗、站内聊天、自动提醒、图片上传和多门店统筹尚未确认为本轮必需功能。

店长联系主人是已确认的业务活动；电话、线下联系或系统消息等具体渠道待明确。主人账号的注册或开通方式同样待明确。

外部协作系统为微信支付或支付宝，承担真实在线支付处理并返回支付结果。五类角色是业务人员角色，加上支付平台共六类参与者；支付平台作为一类外部协作系统建模。具体接入哪一个平台或是否同时支持两者待明确。

## 3. 完整业务流程

| 步骤 | 操作角色与活动 | 系统记录或结果 |
|---|---|---|
| 1. 业务准备及房源开放 | 管理员管理账号权限；前台先核实房间是否可接待，维护房间资料并设置可预约状态；店长查看门店房态和人员安排 | 主人可以浏览已经开放的房源；尚未开放的房间不参与线上预约；具体房型和价格维护规则待明确 |
| 2. 宠物建档 | 主人填写宠物名字、种类、品种、年龄、体重、联系方式、饮食习惯、健康说明和特殊照护要求 | 形成可用于下单及照护的宠物资料 |
| 3. 查看房源与可订日期 | 主人先浏览前台已开放的房源，选择宠物和寄宿日期；系统计算该期间的实际可用房间，供主人选择 | 展示符合宠物条件且整个寄宿期间可用的房源；尚未选日期时只能查看房源介绍或概览，不能据此保证任意日期均有房 |
| 4. 自主预约与全额支付 | 主人选定可订房源后填写预约资料和照护要求，核对费用并提交；系统复核日期与房间可用性，预留一间实际房间、生成待付款订单；主人通过支付平台支付全款 | 平台确认全款支付成功后预约成功、等待到店；无需前台逐笔审核；房间已不可订时提示重新选择；未付或支付失败不显示预约成功，也不记为正式接单或实际入住 |
| 5. 到店核对与正式接单 | 主人带宠物到店；前台核对成功预约、全额付款结果、宠物实际情况、健康说明、照护要求和物品，确认实际接收 | 保存正式接单人员和时间、核对结果及物品信息；不符合接收条件时交店长协调，不能只凭线上确认就记为已接单 |
| 6. 直接派单 | 正式接单后，前台直接指定主负责照护员，将订单及交接要求提供给该照护员，无须店长审批 | 保存分配人、时间和责任人；一名照护员可负责多只宠物 |
| 7. 实际入住与照护交接 | 前台在正式接单及责任分配后登记实际入住，并将宠物与照护要求交接给照护员 | 保存实际入住时间，订单进入寄宿中；明确责任并完成交接后开展照护 |
| 8. 日常照护 | 店长或负责宠物照护员安排照护事项，宠物照护员执行并登记 | 保存计划与实际执行情况，主人和店长可查看 |
| 9. 突发事项处理 | 前台或照护员登记发现的问题并上报，店长查看、联系主人、调配人员或协调处理并保存结果 | 保存上报、联系、处理过程及结果；正常订单无须经过此分支 |
| 10. 核对离店 | 前台核对预约全款记录与实际服务，正常按预约完成时无须再付款；核对接回人、办理宠物及物品交接，登记实际离店并结单；费用变更或其他异常交店长协调 | 保存付款与服务核对、实际离店及交接结果，释放资源、结束责任并保留记录；服务变更的补退费用细则另定 |

线上预约全额支付与线下正式接单已确认。具体平台、计费、未付款预留时限、退款、主动取消、改期、续住、未到店、提前或逾期接回和费用调整仍需细化，见第 8 节。

店长可以随时查看各订单的预约、到店正式接单、责任分配、付款、入住、照护事项完成情况、异常处理及离店进度。店长查看与监督不构成普通订单的审批步骤。

| FR-07 | UC-07 安排照护事项 | 安排事项，记录内容、计划时间和执行人员 | 店长、负责宠物照护员 |
| FR-08 | UC-08 登记照护结果 | 保存执行结果、实际执行人、执行时间及宠物情况 | 宠物照护员 |
| FR-09 | UC-09 查看照护情况 | 主人查看本人宠物的照护记录；店长查看门店照护情况及待完成事项 | 主人、店长 |
| FR-10 | UC-10 上报突发事项 | 前台登记接待中发现的问题，照护员登记宠物异常；记录发生时间和上报人，关联宠物及订单并供店长处理 | 前台接待员、宠物照护员 |
| FR-11 | UC-11 处理突发事项 | 店长查看报告，联系主人、协调处理或调配人员，保存处理过程和最终结果 | 店长 |
| FR-12 | UC-12 核对与离店 | 前台与主人核对已付全款和实际服务，正常按预约完成不再收款；核对接回人、交接宠物与物品、登记实际离店并完成订单；服务变更和费用异常交店长协调 | 主人、前台接待员 |
| FR-13 | UC-13 管理账号与权限 | 支持身份验证及角色访问控制，允许管理员管理账号和分配角色 | 管理员；身份验证涉及全部角色 |
| FR-14 | UC-14 支付预约全款 | 主人在预约阶段核对寄宿费用并通过真实支付平台支付全款；保存订单金额和支付结果，平台确认全款支付成功且有效房间预留存在时预约成功；不以页面跳转或前台人工标记替代平台确认 | 主人、支付平台 |
| FR-17 | UC-17 线下正式接单 | 主人带宠物到店后，前台核对预约与实际情况，预约成功、全款已付且符合接收条件时确认接收，保存接单人员、时间和核对结果；不符合时交店长协调 | 前台接待员 |
| FR-18 | UC-18 查询可预约房源 | 主人浏览前台已开放的房源，按宠物和寄宿日期查询整个期间可订的房间及费用信息；查询本身不预留，提交时重新校验 | 主人 |

寄宿资源采用实际房间管理。前台先维护并开放房源，系统按主人选定日期计算可订房间；提交预约时再核验并预留实际房间，线下正式接单时核对接待安排。房型划分及价格维护权限仍待明确，不把旧版四种房型自动设为固定需求。

### 用例示例：UC-05 安排照护责任

- 主要参与者：前台接待员；店长参与突发事项中的人员调整路径。
- 前置条件：主人已带宠物到店、前台已正式接单，订单未取消或完成，存在适合本次寄宿的照护员。初次分配在正式接单后直接办理，无须店长审批；尚未入住时不能登记实际照护完成。
- 输入：寄宿订单、选定宠物照护员。
- 主流程：前台查看线下已正式接收的订单及照护要求，选择照护员并保存；系统记录分配人和时间，使该照护员可查看订单、计划时间及要求。
- 成功结果：主人、店长和负责宠物照护员看到一致的责任人信息。
- 日常转派路径：前台选择新的照护员并登记交接，保存新的当前责任人和交接记录，原照护记录继续保留实际执行人。
- 突发事项路径：无合适人员可分配或发生突发情况时，上报店长；店长按异常处理需要协调或调整照护人员，记录原因及处理结果。普通分配不经过此路径。
- 失败路径：宠物照护员账号不可用或操作者无权限时拒绝保存、说明原因并保留原结果。
- 已确认：前台直接派单；一名照护员可以负责多只宠物，每次寄宿只有一名当前主负责照护员，转派需保留交接记录；接单分配、实际入住和执行照护分别记录。
- 待明确：是否额外设置店员确认接单步骤、人员容量上限及未完成事项的交接细节。
- 关联：FR-05、BR-02、AC-05。

本轮分区用例布局覆盖本表16个主要用例，另提取3个包含子用例、1个条件扩展用例，并将 UC-05 已有的初次分配与日常转派细化为 UC-05A、UC-05B，分别泛化到 UC-05。共享用例可以在不同角色分区重复展示，仍沿用同一编号和原权限范围；不以角色泛化扩大店长或管理员权限。具体关系见[Visio 绘图说明](../02_UML模型/README.md)。本次仅调整建模层次及排版，不改变已经确认的业务流程。其他详细用例待补齐。登录作为受保护业务的前置条件，包含、扩展或泛化关系应有实际业务依据。

## 5. 业务规则与状态

| 编号 | 规则 | 确认状态 |
|---|---|---|
| BR-01 | 前台房源开放、主人查询并提交预约、支付成功、到店正式接单、派单、入住和完成分别记录；线上不增加逐笔人工审核，预约成功不等于正式接单 | 已确认流程 |
| BR-02 | 前台在线下正式接单后直接指定本次寄宿的一名主负责照护员，无须店长审批；一人可照护多只；前台日常转派、店长异常调配均留交接记录 | 已确认，人员容量及任务交接细节待明确 |
| BR-03 | 事项创建与执行完成分开；完成记录保留实际执行人、时间和结果 | 已确认流程的记录要求 |
| BR-04 | 前台或照护员上报突发事项，店长主要负责联系主人并协调处理、保存结果；异常发生不自动结束订单 | 已确认流程 |
| BR-05 | 主人只处理本人资料；前台接单、分房、派单、办理入住及结算结单；照护员处理分配的照护；店长查看各订单进度、处理突发事项并按需紧急调配；管理员管理账号权限 | 具体操作范围见第 2.1 节 |
| BR-06 | 按原预约完成时，全款已在预约阶段支付；离店核对记录后交接并结单，释放资源、结束责任并保留历史 | 已确认流程，服务变更的补退费用细则待明确 |
| BR-07 | 一单一宠一房；只有前台已开放的房间可被查询预订，系统按日期计算可用性，提交时复核并预留整个寄宿期间；同一房间的有效预留不能时间重叠 | 房源先维护再预约；日期校验及防止重复预留由流程推导 |
| BR-08 | 结束订单时处理尚未执行的照护事项并保留已执行记录 | 建议取消未执行事项，具体关闭规则待细化 |
| BR-09 | 主人自主预约时全额支付寄宿费用，有效房间预留及平台支付成功后预约成功，无需等待前台审核；正常离店不再收取同一笔预约费用 | 已确认，计费和退款细则待明确 |
| BR-11 | 线下正式接单和入住均核对成功预约及全款付款结果；仅有线上付款不能代替实际到店接收 | 根据两阶段业务推导的前置条件 |

主流程：`查询可订房源 → 提交预约（待付款） → 预约成功（待到店） → 待入住（已正式接单） → 寄宿中 → 已完成`。查询发生在订单创建前，不是订单状态。

系统提交校验通过并预留房间后生成待付款订单，平台确认预约全款支付成功后进入预约成功。付款失败或结果未确认时不能进入预约成功。待付款期间的房间预留和释放时限仍待明确，不沿用原定金24小时规则。

线上预约和线下正式接单是两个独立业务步骤。正式接单后由前台直接派单、办理入住，无须店长审批。正式接单与入住可在同一次到店办理中连续完成，分别记录事件和时间，不要求增加重复填单或额外审批页面。

没有可用房间、房源未开放或提交时余量变化，均提示无法预订并引导重新选择，不通过前台事后拒绝替代可用性校验。到店核对不符交店长协调，不误记正式接收；取消、未付款关闭和退款规则待明确。

付款状态单独记录待支付、支付成功或支付失败等平台确认结果。责任分配、照护事项和异常处理分别记录其进展；订单只在满足相应条件时推进。
