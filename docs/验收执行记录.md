## 1. 环境与执行方式

- **运行环境**：Windows（win32 x64）；Node.js v24.16.0。
- **后端产物**：`apps/server/dist/app.js`（TypeScript 编译产物，2026-10-23 10:14 构建），导出
  `createApp({ dbPath, todayOverride }) -> { app, db, today, close }`；空库自动建表并写入种子数据。
- **数据库**：SQLite（Node 内置 `node:sqlite` 的 `DatabaseSync`，WAL 模式）。测试库文件放在仓库内
  `.tmp/acceptance/<场景编号>-<pid>-<序号>.db`，**每个场景独立数据库 + 独立后端实例**；场景结束后先
  `server.close()` 再调用实例 `close()`，随后删除 `.db/-wal/-shm`，两轮执行后无残留文件，Windows 下未见文件占用问题。
- **可重复运行**：不依赖真实日期，不依赖外部服务；同一命令连续执行两轮均为 30/30 PASS（见第 7 节证据）。
- **PB_TODAY 使用说明**：
  - 脚本**不设置宿主环境变量** `PB_TODAY`，而是对每个场景调用
    `createApp({ dbPath, todayOverride })` 注入可控的“今天”，避免污染宿主环境；
  - 统一基准演示日期为 `2026-11-01`（与 MVP 基线计费示例 11-01 至 11-04 一致）；
  - 多阶段日期场景（如 11-01 入住 → 11-03/11-04/11-05 结单、11-02 延迟入住）对**同一数据库**先关闭上一实例、
    再以新 `todayOverride` 重新 `createApp`，验证状态与账单跨“天”一致；
  - 健康检查场景额外验证：不注入 `todayOverride` 时 `GET /api/health` 的 `today` 等于 Asia/Shanghai 真实门店日期，
    注入时 `today` 为注入值且 `clockOverridden=true`。
- **预置账号**：ownerA/owner123、ownerB/owner123、staff/staff123、admin/admin123（种子数据，含 ownerB 的猫「糖糖」）。
- **场景隔离**：每个场景独立 SQLite 文件；同场景内不同阶段共享同一数据库文件。断言失败时打印场景编号、请求方法/路径/请求体、
  实际响应 JSON、预期值/实际值差异与最近 25 条接口交互，并以退出码 1 结束。

## 3. 关键金额与状态证据（可人工核对）

- 基础示例（80 元/天 × 11-01~11-04，计划 3 天）：基础费 `24000` 分。
- 11-03 提前接回：`overdueDays=0`、`overdueFeeFen=0`、`totalFen=24000`（不减费）。
- 11-05 离店：`overdueDays=1`、`overdueFeeFen=8000`、`totalFen=32000`（仅基础费+逾期费）。
- 调价不追溯：旧单 `dailyPriceSnapshotFen=8000/baseFeeFen=24000`；调价 9000 后新单 `9000/27000`。
- 价格变化确认：409 `PRICE_CHANGED`，`details={dailyPriceFen:9000,plannedDays:3,totalFen:27000}`，未创建预约；重新确认后按 9000 创建。
- 结单：`settled=true`、`invoice.status='paid'`、`receipt.amountFen=totalFen`（全额线下收款，现金/转账）、预约 `completed`、入住 `checkOutAt` 非空；未确认核对时 400 `PAYMENT_INVALID` 且保持 `checked_in`。
- 业务日期：`computedOn`、`actualCheckInDate`、`actualCheckOutDate` 均跟随 `todayOverride`（演示日期），操作时分秒取真实时刻（见 docs/API.md §6）。
