# 宠物寄养预约与照护管理系统软件需求规格说明书

版本V1.2，2026-10-23。用于单门店Web MVP需求建模与后续实现。课程业务设计未经真实门店访谈，以下需求与验收场景不代表系统已实现或通过测试。

## 一 目标与角色

通过一个可在电脑和手机浏览器访问的网站，完成宠物建档、预约、分房、入住、照护和线下结算。主人端适配手机，管理端优先适配电脑。

主人只能管理本人宠物、预约及查看照护和账单。工作人员负责审核、分房、入住、照护、线下收款及手动标记失约。管理员维护房型日价和房间基础资料。预设账号及角色，不提供人员管理界面；管理员需要业务操作时另授工作人员角色。

## 三 业务规则

| 编号 | 规则 |
|---|---|
| BR01 | 一张预约属于一个主人并关联其名下一只宠物；一宠一间。按正常操作检查该宠物已确认或已入住预约的重叠区间。 |
| BR02 | 日期按Asia/Shanghai解释。区间为[startDate,endDate)，开始日不早于提交当日，开始日早于离店日，计划天数为自然日差，至少一天。不做小时级限制与收费。 |
| BR03 | 提交时由服务端读取房型日价并保存快照；与主人页面已确认价格不一致时先重新确认。待审核不占房；通过审核分配具体房间后占用计划区间，审核不再改价。 |
| BR04 | 待审核、已确认预约可免费取消，无预付款；已入住不可取消。到计划离店日仍未入住，由工作人员手动标记失约并释放计划占用。无自动扫描。 |
| BR05 | 已确认且startDate≤实际入住日<endDate时可入住；延迟到店需原因，不调整原定离店日与基础费用。资料核验通过才登记入住。 |
| BR06 | 查询和普通审核排除与已确认/已入住订单计划区间重叠的房间及当前实际占用房间；入住前再检查实际空闲。两个区间相交条件为a.start<b.end且b.start<a.end。并发协调和逾期占房后续处理延期。 |
| BR07 | 在住期间可建照护任务并登记执行人员、计划时间、完成时间和文字说明；任务状态为待完成、已完成、已取消。离店取消待完成任务，保留全部历史；完成记录首版不做更正。 |
| BR08 | 自动提醒不进入本版，原提醒时间与扫描周期不作为验收条件。 |
| BR09 | 基础费=锁定日价×原计划天数；提前接回和延迟入住均不减费。逾期天数=max(0,实际离店日−计划离店日)，逾期费=逾期天数×锁定日价。应收为二者之和，金额以人民币分保存。 |
| BR10 | 本版无附加项目与额外收费，账单只展示基础费、逾期费及合计。 |
| BR11 | 实际离店日不早于实际入住日，以办理当日为准，不支持回填改价。主人核对，工作人员确认现金或线下转账全额收款后结单并释放实际占用。未确认收款时保持在住。结单保存应作为一个业务事务；故障注入与重试恢复不纳入本轮验收。 |
| BR12 | 房型固定为猫舍标间、猫舍豪华间、犬舍标间、犬舍豪华间。房型统一日价，房间有最大体重限制。主人选房型，工作人员分配同房型的匹配房间；改价不追溯已提交订单。 |

房间查询采用“同一间房覆盖整个区间”的计数。例如A房只空前半段、B房只空后半段，均不算全程可用。首版保守排除当前实际占用房间，即使查询的是未来日期；未来房态精细预测不在本版。

## 四 状态及前置条件

| 原状态 | 操作和条件 | 目标状态 |
|---|---|---|
| 无 | 主人提交有效预约并确认当前价格 | 待审核 |
| 待审核 | 工作人员通过并分配可用房间 | 已确认 |
| 待审核 | 工作人员填写驳回原因 | 已驳回 |
| 待审核或已确认 | 有权操作人取消未入住预约 | 已取消 |
| 已确认 | 当日达到计划离店日且未入住，工作人员标记 | 已失约 |
| 已确认 | 在允许日期内，资料通过、实际空房，登记入住 | 已入住 |
| 已入住 | 核对账单并登记全额线下收款、结单 | 已完成 |

终态为已驳回、已取消、已失约、已完成。无定义的转换不提供操作；服务端进行简单前置检查，首版不设计专门的异常恢复页面或协调流程。过去日期仍待审核的申请由工作人员驳回或取消，不自动处理。

## 五 数据字典

| 对象 | 最小字段 | 约束 |
|---|---|---|
| Account | id、displayName、loginName、passwordHash、roles | 预设账号，角色可多选，不提供公开注册 |
| Pet | id、ownerId、name、species、weight、contact、careNotes、vaccineNotes | 猫或犬、体重大于0、联系人必填 |
| RoomType | id、name、species、dailyPriceFen | 固定四类，金额非负 |
| Room | id、roomTypeId、name、maxWeight | 编号唯一，最大体重大于0 |
| Reservation | id、ownerId、petId、roomTypeId、roomId、startDate、endDate、dailyPriceSnapshotFen、status、createdAt、reviewedBy、reviewedAt、reason | 提交时快照必填；待审核roomId可空，确认后必填；reason用于驳回、取消或失约 |
| Stay | id、reservationId、checkInAt、checkOutAt、inspectionNotes、lateReason、checkInStaffId | 一单至多一次入住，迟到填写原因，未离店checkOutAt为空 |
| CareTask | id、stayId、kind、plannedAt、instruction、status | 类型为喂食、饮水、清洁或其他；计划在实际入住后、计划离店前；逾期在住可继续安排当日任务 |
| CareRecord | id、taskId、staffId、completedAt、notes | 一任务至多一条文字完成记录 |
| Invoice | id、stayId、plannedDays、dailyPriceSnapshotFen、baseFeeFen、overdueDays、overdueFeeFen、totalFen、status | 一次入住至多一张有效账单，未收款前按当日重新计算 |
| Receipt | id、invoiceId、amountFen、method、staffId、paidAt | 一单一条全额登记，现金或线下转账 |

使用记录中的操作者与时间支持最基本追溯，不提供本版之外的审计中心。Reminder与附加ChargeItem不属于本版必需对象。照护说明为主人提供的信息，系统不提供诊断或处方。

## 六 页面范围

主人端：登录、宠物列表/编辑、房型日期查询、预约确认、订单列表/详情、照护与账单查看。管理端：预约审核、入住登记、在住列表、照护任务、离店结算、房型价格与房间资料。账号管理、提醒中心、通知中心和图片上传页不进入本版。

## 七 质量要求与验收边界

必须保留：服务端角色与归属检查、密码散列存储、必填及数值日期校验、普通房态检查、业务状态前置条件、金额准确、刷新后数据保留及基本移动端可读性。

首版采用单人按顺序操作的演示验收。并发审核协调、专门幂等接口、故障补偿、失败重试、取消与入住竞争、检查不通过的后续流程暂缓。普通非法输入或不满足前置条件时简单提示，不构建专门异常子系统。此边界不宣称并发和故障情况下已验证正确。

旧版性能压测、备份恢复目标与部署安全检查移至后续部署评估，不写成已完成结果。首次验收见05_核对与答辩/01_验收场景.md。
